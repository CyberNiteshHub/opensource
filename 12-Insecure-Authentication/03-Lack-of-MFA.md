# Module 12: Insecure Authentication - Lack of Multi-Factor Authentication

## Overview

Multi-Factor Authentication (MFA) adds an extra layer of security beyond just a password. Without MFA, a stolen password is enough to access an account.

## What is Multi-Factor Authentication?

MFA requires two or more factors to authenticate:

**Three factors:**
- Something you **know** (password, PIN)
- Something you **have** (phone, hardware token)
- Something you **are** (fingerprint, face)

**Examples of MFA:**
- Password + SMS code
- Password + authenticator app code
- Password + fingerprint
- Password + hardware key

## Why MFA is Important for Mobile Apps

Mobile apps handle sensitive data. A stolen password should not be enough to access them.

**Without MFA:**
```
Password stolen -> Account compromised
```

**With MFA:**
```
Password stolen -> Still need second factor -> Account safe
```

## Common MFA Methods for Mobile

### 1. SMS/Text Message Codes

A code is sent to the user's phone via SMS.

**Pros:**
- Works on all phones
- Easy to implement

**Cons:**
- SIM swapping attacks
- SMS interception
- Relies on cellular network
- Phishing-prone

### 2. Authenticator App (TOTP)

A time-based code generated by an app (Google Authenticator, Authy).

**Pros:**
- No network required
- Works offline
- More secure than SMS

**Cons:**
- User must install another app
- Backup codes needed

### 3. Push Notifications

A notification is sent to the user's device asking to approve or deny the login.

**Pros:**
- Easy for users
- Shows login context (location, device)

**Cons:**
- Push fatigue (users approve without thinking)
- Requires internet connection

### 4. Biometric Authentication

Fingerprint or face recognition.

**Pros:**
- Very convenient
- Hard to steal (but not impossible)

**Cons:**
- Device-dependent
- Biometrics can be spoofed
- Privacy concerns

### 5. Hardware Security Keys

Physical USB or NFC keys (YubiKey, Google Titan).

**Pros:**
- Very secure
- Phishing-resistant

**Cons:**
- Requires physical key
- Expensive to distribute
- Inconvenient

## Vulnerabilities Without MFA

### Case 1: Password Reuse Attack

1. User has the same password for multiple sites
2. One site is breached
3. Attacker has the password
4. Attacker accesses the mobile app

**Without MFA:** Account compromised
**With MFA:** Account safe (attacker does not have the second factor)

### Case 2: Phishing Attack

1. User receives a fake login page
2. User enters their password
3. Attacker now has the password

**Without MFA:** Account compromised
**With MFA:** Account safe (attacker does not have the second factor)

### Case 3: Credential Stuffing

1. Attacker has a list of stolen passwords from other breaches
2. Attacker tries them on the mobile app
3. Some passwords match

**Without MFA:** Account compromised
**With MFA:** Account safe

## MFA Implementation Issues

Even when MFA is implemented, it can be insecure.

### Issue 1: No MFA for Sensitive Actions

Some apps only require MFA for login, not for sensitive actions.

**Examples:**
- Changing password without MFA
- Adding a new payee without MFA
- Making large transfers without MFA

### Issue 2: Weak Fallback

When biometrics fail, the app falls back to an insecure method.

```java
if (biometricAuthSuccessful()) {
    grantAccess();
} else {
    // Fallback to just password (no MFA)
    if (passwordAuthSuccessful()) {
        grantAccess(); // MFA bypassed!
    }
}
```

### Issue 3: MFA Bypass via API

The mobile app may require MFA, but the API may not enforce it.

**Attack:**
1. Intercept the login request with Burp Suite
2. Remove the MFA code from the request
3. Send the request without MFA
4. Server accepts it (bypasses MFA)

### Issue 4: Remember Device Without MFA

Some apps allow users to "remember this device" and skip MFA.

```java
// After first MFA, skip MFA for 30 days
sharedPreferences.putLong("mfa_expiry", System.currentTimeMillis() + 30 * 24 * 60 * 60 * 1000);
```

If the token is stored insecurely, attackers can skip MFA permanently.

## Testing for MFA Issues

### Test 1: Check if MFA is Required

```
1. Create an account
2. Try to log in from a new device
3. If no MFA prompt, MFA is not required
```

### Test 2: Check MFA Bypass

```
1. Set up Burp Suite
2. Log in with valid credentials
3. Intercept the MFA submission
4. Remove the MFA code from the request
5. Forward the request
6. If access is granted, MFA is bypassable
```

### Test 3: Check Sensitive Actions

```
1. Log in (with MFA)
2. Try to change password without MFA
3. Try to transfer money without MFA
4. If allowed, sensitive actions lack MFA
```

## Best Practices for MFA

| Practice | Description |
|----------|-------------|
| Always require MFA | For all users, not optional |
| MFA for sensitive actions | Changing password, payments |
| TOTP over SMS | Authenticator apps are more secure |
| Rate limit MFA attempts | Prevent brute force on codes |
| Secure fallback | Do not weaken security on fallback |
| Enforce on server | Do not trust client-side MFA checks |

## Summary

Lack of MFA is a critical vulnerability. A stolen password alone should not be enough to access an account. Implement MFA using TOTP or push notifications (preferred over SMS). Require MFA for all sensitive actions. Enforce MFA on the server side, not just the client side.
